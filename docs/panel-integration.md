# Panel integration guide

This guide is for developers of XiaoBoard, Xboard, V2Board, Remnawave and compatible panels
who want to offer TunnixNode as a node backend.

## Summary

TunnixNode uses the node APIs that panels already expose for v2node, Xboard nodes and
remnawave/node. **No API change is required.** Integration consists of:

1. Showing an install command for TunnixNode next to the existing one (section 2).
2. Optionally labelling nodes that report the `TunnixNode/<version>` User-Agent (section 5).

## 1. APIs used

### XiaoBoard, Xboard, V2Board (node pulls from the panel)

Every request carries `token`, `node_id` and `node_type` as query parameters and
`Accept: application/json`.

| Purpose | Method and path | XiaoBoard | Xboard | V2Board |
|---|---|:---:|:---:|:---:|
| Node configuration | `GET /api/v2/server/config` (`node_type=v2node`) | Yes | Yes | - |
| Node configuration | `GET /api/v1/server/UniProxy/config` (`node_type=<protocol>`) | - | - | Yes |
| Users | `GET /api/v1/server/UniProxy/user` | Yes | Yes | Yes |
| Traffic | `POST /api/v1/server/UniProxy/push` | Yes | Yes | Yes |
| Online IPs | `POST /api/v1/server/UniProxy/alive` | Yes | Yes | - |
| Device counts | `GET /api/v1/server/UniProxy/alivelist` | Yes | Yes | - |
| Load status | `POST /api/v1/server/UniProxy/status` | - | Yes | - |

Polling follows `base_config.pull_interval` and `push_interval` (seconds, default 60).
Configuration changes are detected by ETag and by a hash of the response body, so the
XiaoBoard `/api/v2/server/config` ETag quoting issue does not matter.

### Remnawave (panel pushes to the node)

TunnixNode implements the remnawave/node HTTPS API on `NODE_PORT`: TLS 1.3, client certificate
signed by the panel CA, RS256 JWT, `SECRET_KEY` payload as generated by the panel. It reports
`nodeVersion` `3.4.6` (the contract version it implements) and its own version as `xrayVersion`.

## 2. Install command

The installer accepts the same `--api-host`, `--node-id` and `--api-key` flags as the v2node
installer, plus `--panel`.

```text
wget -N https://raw.githubusercontent.com/huzgnm/tunnix-node/main/scripts/install.sh && bash install.sh --panel <PANEL> --api-host '<API_URL>' --node-id <ID> --api-key '<SERVER_TOKEN>'
```

| `--panel` | Panel |
|---|---|
| `xiaoboard` | wyx2685/v2board (v2node node table) |
| `xboard` | cedar2025/Xboard |
| `v2board` | v2board/v2board 1.7.x; also pass `--node-type vmess`, `trojan` or `shadowsocks` |
| `remnawave` | Remnawave; pass `--secret-key '<SECRET_KEY>' --node-port <PORT>` instead of the API flags |

Optional flags: `--mode systemd` (default is Docker), `--version vX.Y.Z`, `--bbr`.
Running the command again with another node ID adds that node to the same instance.

### XiaoBoard example

In `app/Services/ServerService.php`, `getAllV2node()`, next to `install_command`:

```php
$servers[$k]['tunnix_install_command'] = sprintf(
    'wget -N https://raw.githubusercontent.com/huzgnm/tunnix-node/main/scripts/install.sh && bash install.sh --panel xiaoboard --api-host %s --node-id %d --api-key %s',
    $apiHostArg,
    $nodeId,
    $apiKeyArg
);
```

### Xboard example

Xboard generates install commands per machine only. A per-node command can be built from the
same settings:

```php
$command = sprintf(
    'wget -N https://raw.githubusercontent.com/huzgnm/tunnix-node/main/scripts/install.sh && bash install.sh --panel xboard --api-host %s --node-id %d --api-key %s',
    escapeshellarg((string) admin_setting('app_url')),
    (int) $server->id,
    escapeshellarg((string) admin_setting('server_token'))
);
```

### Remnawave

Either show the install command:

```text
wget -N https://raw.githubusercontent.com/huzgnm/tunnix-node/main/scripts/install.sh && bash install.sh --panel remnawave --secret-key '<SECRET_KEY>' --node-port <NODE_PORT>
```

or offer a docker-compose file. The environment variables are the same as remnawave/node:

```yaml
services:
  tunnix-node:
    image: ghcr.io/huzgnm/tunnix-node:latest
    container_name: tunnix-node
    restart: always
    network_mode: host
    cap_add: [NET_ADMIN]
    ulimits:
      nofile: { soft: 1048576, hard: 1048576 }
    environment:
      - NODE_PORT=2222
      - SECRET_KEY=<SECRET_KEY>
```

## 3. Node configuration fields

Field names and aliases of XiaoBoard and Xboard are both accepted (`network_settings` /
`networkSettings`, `obfs_password` / `obfs-password`, `tls_settings.cert_mode` /
`cert_config.cert_mode`, `hysteria` with `version: 2`, VLESS `encryption_settings` / `decryption`).

| Area | Supported |
|---|---|
| Protocols | VLESS, VMess (AEAD), Trojan, Shadowsocks (AEAD, 2022), Hysteria2, TUIC v5, AnyTLS |
| `network` | `tcp`, `ws`, `grpc`, `httpupgrade`, `xhttp` / `splithttp` |
| `tls` | 0 none, 1 TLS, 2 REALITY (`server_name(s)`, `dest`, `server_port`, `private_key`, `short_id(s)`, `mldsa65Seed`) |
| `flow` | `xtls-rprx-vision` |
| `cert_mode` | `http`, `dns` (Cloudflare), `file`, `remote`, `self` |
| Hysteria2 `obfs` | `salamander` |
| `routes` | `block` (bare keyword, `domain:`, `full:`, `keyword:`, `regexp:`), `block_ip` (IP, CIDR), `block_port` (ports, ranges), `protocol` `quic` (UDP port 443); matched as Xray does |
| `base_config` | `push_interval`, `pull_interval`, `node_report_min_traffic`, `device_online_min_traffic` |
| Users | `id`, `uuid`, `speed_limit` (Mbit/s), `device_limit` |

Not supported: mKCP, Hysteria v1, multi-user Shadowsocks 2022 with ChaCha20, REALITY `xver`,
route actions `route`, `route_ip` and `default_out` (traffic leaves the node directly),
`geosite:` / `geoip:` / `ext:` matches, and protocol matches other than `quic`.
Unsupported route rules and matches are skipped one by one with a warning in the log; the node
keeps running with the rest of its configuration. Unsupported protocols or transports are reported as an
error; a running node keeps its previous configuration and a new node retries until the
configuration is valid.

Remnawave profiles: VLESS, VMess, Trojan, Shadowsocks and Hysteria inbounds with the transports
above are served; other inbounds (socks, dokodemo-door, tun, ...) are ignored. Plugins
(`/node/plugin/*`) answer `accepted: false`; `drop-ips` is accepted without effect.

## 4. Reporting behaviour

| Item | Behaviour |
|---|---|
| Traffic | Bytes exchanged with destinations, as Xray counts them. Each push carries the delta since the last successful push. |
| Failed push | The delta is kept and sent again with the next push; nothing is lost or double counted. |
| Users below `node_report_min_traffic` (KB) | Not pushed; their traffic accumulates until it exceeds the threshold. |
| Removed users | Disconnected at the next user sync; their remaining traffic is still pushed. |
| Online IPs (`alive`) | Plain IP addresses, once per push interval. Users below `device_online_min_traffic` (KB) are left out. |
| Device limit | A new IP is refused when the panel's `alivelist` count for the user has reached `device_limit`, as in v2node. |
| Speed limit | Per user, shared by all of the user's connections on the node. |
| DNS | Client DNS queries to port 53 are answered by the server's resolver, as in v2node. |

## 5. Identifying TunnixNode

Requests from TunnixNode carry `User-Agent: TunnixNode/<version>`. A panel can store it to show
the node software and version in the node list. Remnawave panels can read the version from the
`xrayVersion` field of `/node/xray/healthcheck`.

## 6. Versions

Releases: <https://github.com/huzgnm/tunnix-node/releases>. The installer and the `tunnix update`
command always fetch the latest release unless `--version` is given.
